# US-07 — Filter tasks by status

| Field | Value |
|---|---|
| **ID** | US-07 |
| **Layer** | Backend |
| **Actor** | Task owner |
| **Linked endpoint** | `GET /api/tasks?status={status}` — combinable with `search` |
| **Spec user story** | Story 7 — Focus on one state of work (P3) |
| **Priority** | P3 |

## Description

As the task owner, I want to narrow the task list to a single state — Todo, InProgress or Done —
so that I can concentrate on outstanding work or review what I have finished. Like search, this is
a parameter on the existing list endpoint.

## Acceptance criteria

- **AC-07.1** — Supplying a status responds `200 OK` with only tasks in that state.
- **AC-07.2** — Omitting the status returns tasks in every state.
- **AC-07.3** — A status outside the permitted set is rejected with `400 Bad Request`; it is never
  silently ignored and never returns an unfiltered list.
- **AC-07.4** — A status with no matching tasks responds `200 OK` with an empty collection.
- **AC-07.5** — **Search and status combine.** Supplying both returns only tasks that satisfy both
  conditions.
- **AC-07.6** — All four combinations behave correctly: neither parameter, search only, status
  only, and both together.
- **AC-07.7** — Results remain ordered newest first.
- **AC-07.8** — Filtering is applied by the database query, not in memory.
- **AC-07.9** — The query is executed asynchronously.

## Traceability

**Satisfies**: FR-019, FR-020, FR-021, FR-027

**Verified by success criteria**: SC-006

## Out of scope

The filter control (US-13). Filtering by importance or due date. Selecting several states at once.

## Definition of done

Demonstrated in Swagger across all four parameter combinations, plus an invalid status value
returning `400`.
