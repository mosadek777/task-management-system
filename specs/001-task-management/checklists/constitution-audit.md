## Article V — DTO Boundary + Server-Side Validation ✅ PASS

**Requirement**: entities never cross the controller boundary; server-side validation mandatory and
authoritative.

**Evidence** — `TaskItem` appears in **zero** files under `Controllers\` or `DTOs\` (excluding
comments). Every action signature is DTO-typed:

```
Task<ActionResult<IEnumerable<TaskResponseDto>>> GetAll(...)
Task<ActionResult<TaskResponseDto>>              GetById(int id)
Task<ActionResult<TaskResponseDto>>              Create([FromBody] CreateTaskDto dto)
Task<ActionResult<TaskResponseDto>>              Update(int id, [FromBody] UpdateTaskDto dto)
Task<IActionResult>                              Delete(int id)
```

**Over-posting is structurally impossible**: neither input DTO declares `Id` or `CreatedAt`.
Verified live — posting `{"id":99,"createdAt":"1999-01-01"}` returns a server-generated id and a
`createdAt` of now.

**Server-side validation is authoritative**: Data Annotations on both input DTOs, enforced by
`[ApiController]` before any action body runs. Proven by seven live rejection classes (missing,
empty and whitespace-only title; 201-char title; 1001-char description; invalid priority; invalid
status), each returning `400` with nothing stored. Client-side Angular rules mirror these but are
never the enforcement point — a server rejection still surfaces in the UI (AC-09.13, AC-10.12).

## Article VI — Async All The Way ✅ PASS

**Requirement**: every database operation asynchronous; `.Result`, `.Wait()`,
`.GetAwaiter().GetResult()` and synchronous EF methods forbidden.

**Evidence**:

- Grep across all backend `.cs` (excluding `bin`, `obj`, generated `Migrations`) for
  `.Result` / `.Wait()` / `.GetAwaiter().GetResult()` → **zero hits**.
- Grep `TaskService.cs` for synchronous EF materialising calls (`.ToList(`, `.FirstOrDefault(`,
  `.SingleOrDefault(`, `.Any(`, `.Count(`, `.SaveChanges(`) → **zero hits**. Every one is the
  `Async` variant and every one is awaited.
- All five controller actions are `async Task<...>`.

`_context.Tasks.Add(...)` and `.Remove(...)` are synchronous **correctly** — they mutate the local
change-tracker and touch no database. The database work happens in the awaited `SaveChangesAsync()`.

## Advisories — LOW, no article breached

### Advisory 1 — `Microsoft.AspNetCore.OpenApi` is unused

`Program.cs` was rewritten to use Swashbuckle (`AddSwaggerGen` / `UseSwagger` / `UseSwaggerUI`), so
the template's `AddOpenApi()` and `MapOpenApi()` calls no longer exist. The package reference
remains with **no code reference**.

**Not a violation**: Article III bans *third-party* packages, and this is first-party
Microsoft, template-supplied; plan.md §4.1 requires exactly four entries and there are exactly four.

**Why it still matters**: it invites the reader to believe two OpenAPI mechanisms are in play when
only one is. Fix is one line:

```powershell
cd C:\Users\moham\OneDrive\Desktop\project\backend\TaskManagement.Api
dotnet remove package Microsoft.AspNetCore.OpenApi
```

### Advisory 2 — test scaffolding with no tests

`package.json` declares `"test": "ng test"` and `vitest` + `jsdom` are in `devDependencies`, and
`tsconfig.spec.json` exists — but there are **0 `.spec.ts` files** (the template's `app.spec.ts`
was removed during T-42, since the constitution's scope ceiling excludes automated tests).

**Not a violation**: the scope ceiling forbids *writing* automated tests, not leaving the CLI's
default scaffolding in place.

**Why it still matters**: `npm test` would run a suite containing nothing, which reads as "tests
pass". Either remove `tsconfig.spec.json`, the `test` script and the two dev dependencies, or leave
them deliberately for post-project work. **Owner's call** — Governance requires a FAIL to be fixed
or waived, and this is not a FAIL, so nothing is blocked either way.
